# Правила проекта для агента

Сайт подрядчика: электромонтаж и слаботочные системы (СКС, пожарная
сигнализация, видеонаблюдение, СКУД). Компания в Йошкар-Оле, работает по
всей России. Клиенты — и юрлица, и частники.

## Общение
- С владельцем — по-русски. Английский только в коде, именах файлов, командах.
- Всё, что видит посетитель сайта или пользователь админки, — по-русски.
- Перед принципиальным отклонением (библиотека, формат данных, подход,
  источник данных) — сначала вопрос, потом работа.

## Команды
Всё запускается через Sail из корня проекта:
- первый запуск: `bin/setup`
- поднять / остановить: `./vendor/bin/sail up -d` / `./vendor/bin/sail stop`
- **гейты: `./vendor/bin/sail composer check`** (формат → статанализ → тесты)
- миграции с нуля и демо-данные: `./vendor/bin/sail artisan migrate:fresh --seed`
- журнал воркера очереди (уведомления): `./vendor/bin/sail logs -f queue`
- боевой сервер: `deploy/` и [docs/server.md](docs/server.md). Слитый в
  `main` код сервер забирает сам за 5 минут; миграции — тоже сам.
  Миграции поэтому только обратимо-безопасные: без удаления данных.
- первый администратор на проде: `php artisan admin:create почта`

## Перед каждым коммитом
1. `sail composer check` — зелёный. Хук `.githooks/pre-commit` проверит то же.
2. Одна задача — один коммит. Сообщение по-русски: что и почему, не «фиксы».
3. Изменения внешнего вида — со скриншотом после правки. «Готово» без
   скриншота не говорить.

## Запреты
- Не пушить в `main` напрямую, когда появится удалённый репозиторий: ветка → PR.
- Секреты, пароли, ключи — только в `.env`. В файлах репозитория — имена
  переменных, никогда значения. Демо-пароли не хардкодить: генерировать.
- Работать с копией данных, не с боевой базой.
- Не править `vendor/`, `public/build/`, опубликованные ассеты Filament.
- Не понижать уровень PHPStan и не добавлять игноры, чтобы «стало зелёным».
- Без микросервисов, своих ORM, отдельного фронт-репозитория, новых
  библиотек без вопроса.

## Код
- `declare(strict_types=1)`, типы у всех аргументов, возвратов и свойств.
- Тонкие контроллеры, логика в сервисах (`app/Services`), зависимости —
  через конструктор. Без статических хелперов и глобального состояния.
  Исключения: фабричные `fromX()` у value-объектов, методы enum и
  Filament-ресурсы (статичны по устройству фреймворка — бизнес-логику в
  них не класть, только описание полей и колонок).
- Второй похожий блок — выносить в общее, не копировать.
- Не хранить то, что можно вычислить (например, «цена от» услуги считается
  из прайса, а не лежит колонкой).

## Деньги
- В БД — копейки, целое `bigint`, колонка с суффиксом `_kopecks`.
- Никакого float. Показ и ввод — только через `App\Services\RubleFormatter`
  (`format()` для людей, `toInput()`/`parse()` для полей ввода), проверка
  ввода — правило `App\Rules\RublesAmount`. Образец — прайс (`PriceItem`).

## Права и валидация — сразу
- Роли и права: `app/Enums/Role.php` и `app/Enums/Permission.php`. Новая
  сущность — новые права в `Permission`, раздача в `Role::permissions()`,
  политика в `app/Policies`.
- Права и скрывают (пункта нет в меню), и блокируют (403 по прямой ссылке).
  Filament делает это сам по политике — политика обязательна.
- Каждое поле формы валидируется по схеме БД: длина строки = размеру
  колонки, числа с границами, перечисления — enum, уникальные — unique.

## Эталон
Сущность «Услуга» (`Service`) сделана целиком и служит образцом:
миграция → модель с enum-кастами → фабрика → политика → Filament-ресурс
с валидацией → публичные страницы через сервис → тесты → демо-данные.
Новую сущность делать по её образцу, в том же порядке и с теми же тестами.

«Заявка» (`Lead`) — образец сущности, которая приходит с сайта: публичная
форма через FormRequest → сервис `LeadIntake` → задача в очередь. Поля
клиента в админке только для чтения, менеджер меняет статус и заметку.

«Объект» (`Project`) — образец сущности с файлами: фото на диске `public`
в папке `portfolio` (`App\Services\ProjectPhotos`), убранные и удалённые
фото стирает `ProjectObserver`. Связь с услугами — многие ко многим.

## Уведомления о заявках
- Каналы — классы с интерфейсом `App\Services\LeadNotifications\LeadChannel`,
  список — в `LeadNotifier::channels()`. Новый канал (MAX, SMS) = новый класс.
- Куда слать (адреса, чат) — в админке, таблица `notification_settings`.
  Токены ботов — только в `.env` (`TELEGRAM_BOT_TOKEN`), в БД и коде их нет.
- Отправка идёт в очереди (Redis, сервис `queue` в compose). Одна попытка:
  сбой канала пишется в журнал, остальные каналы отправляются.
- Внешние запросы в тестах — только через `Http::fake()` / `Mail::fake()`.

## Грабли
- `Model::shouldBeStrict()` включён вне прода: ленивая загрузка связей
  падает. Грузите связи явно (`with()`), это не баг.
- PHPStan упал странно — очистить кеш (`.phpstan-cache`) и перегнать.
- Тесты идут на PostgreSQL (БД `testing`), не на SQLite: так ловим разницу
  в SQL до прода.
- Название компании — «ЭлектроСтрой Марий Эл», но оно в `.env` (`SITE_COMPANY_NAME`):
  в коде и шаблонах не хардкодить, брать из `$site`.
- Сессию агента запускать из корня проекта.
- Письма локально не уходят: `MAIL_MAILER=log`, текст писем — в
  `storage/logs`. Настоящая отправка — SMTP в `.env` на сервере.
